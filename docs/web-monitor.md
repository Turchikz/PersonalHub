# Web Monitor

Web Monitor — приложение `monitoring` внутри PersonalHub. Карточка на главной
показывает состояние сайта, время проверки, последние 10 результатов и последние
10 уведомлений. Полная история доступна в Django Admin.

## Начальные настройки

Миграция создаёт монитор Rozetked: `https://rozetked.me/`, интервал 15 минут,
таймаут 10 секунд, контрольный сайт `https://ya.ru/`.
В `/admin/monitoring/monitor/` можно изменить оба URL, интервал (1–1440 минут),
таймаут (1–30 секунд), название и включить/отключить проверки.
Контрольный сайт должен быть доступен при ограничениях у конкретного оператора;
при необходимости замените `ya.ru` на подходящий адрес. Это исходная настройка,
а не гарантия доступности у любого оператора.

## Состояния

| Состояние | Условие |
| --- | --- |
| Онлайн | Основной сайт отвечает HTTP 200–399 после обработки редиректов |
| Возможны белые списки | Основной сайт не даёт HTTP-ответа, контрольный сайт отвечает успешно |
| Сайт недоступен | Основной сайт отвечает ошибкой HTTP или зацикленным редиректом |
| Проблема подключения | Основной сайт не даёт HTTP-ответа, контрольный сайт тоже не отвечает успешно |
| Ещё не проверен | Нет начального результата или изменены URL |
| Приостановлен | Проверки выключены |
| Проверки устарели | Нет результата дольше двух интервалов + 1 минута |

При каждом неуспешном запросе делается одна повторная попытка. Контрольный сайт
проверяется только при недоступности основного. HTTP 403/404/5xx не служит
доказательством белых списков. Время ответа измеряется до получения заголовков;
полная страница не скачивается. Таймаут применяется к блокирующим сетевым
операциям; редиректы могут увеличить длительность всей проверки.

Недоступность одного внешнего сайта не позволяет достоверно установить режим
оператора. Даже при доступном контрольном сайте возможны DNS, TLS или отдельный
сбой Rozetked. Поэтому в интерфейсе используется формулировка «Возможны».
Если недоступны оба сайта, причина также неизвестна, а не обязательно пропал весь
интернет. Проверки отражают подключение Raspberry Pi: проводное дома или раздачу
с телефона в поездке. VPN, работающий на уровне системы, может изменить результат.
HTTP-прокси из переменных окружения для проверок не используются.

## Уведомления внутри сайта

При изменении состояния сохраняется уведомление в БД. Повторное обнаружение того
же состояния не создаёт уведомления. Первая проверка задаёт исходное состояние,
без уведомления. Переход из «Возможны белые списки» в «Онлайн» сообщает об
исчезновении признаков ограничений.

Открытая страница читает сохранённые результаты каждые 30 секунд и показывает
всплывающее уведомление при новом изменении. Сетевую проверку сайта этот опрос
не запускает. Просмотренные уведомления запоминаются в текущем браузере.
При закрытой странице проверки и запись уведомлений продолжаются; история
доступна после возвращения. Push-уведомления вне открытого сайта не используются.

## Запуск и развёртывание

При запуске существующего Docker Compose отдельный сервис `monitor` стартует после
готовности `web` и применения миграций. Он проверяет расписание раз в 10 секунд.
Интервал отсчитывается от завершения предыдущей проверки; после перезапуска
выполняется одна просроченная проверка без воспроизведения всех пропущенных.
Настройки и расписание хранятся в PostgreSQL. Celery/Redis не нужны.

```bash
docker compose -f compose.yaml -f compose.pipertts.yaml up -d --build --wait
docker compose -f compose.yaml -f compose.pipertts.yaml logs --tail 50 monitor
```

Существующий workflow деплоя запускает этот сервис автоматически после попадания
изменений в `main` и успешного CI. До слияния PR работающий Raspberry Pi не меняется.

Для локальной разработки с активным виртуальным окружением:

```bash
python manage.py migrate
python manage.py runserver
# В другом терминале с тем же окружением:
python manage.py run_monitors
```

Один проход по мониторам, срок проверки которых уже наступил:

```bash
python manage.py run_monitors --once
```

При изменении настроек через Admin следующая проверка назначается сразу.
История сохраняет URL, которые использовались во время проверки.
Мониторы одного сайта сериализуются блокировкой строки PostgreSQL, чтобы
параллельный запуск worker не дублировал результат и уведомление.

## Проверка

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python -m pytest
```

Тесты моделируют ответы и сетевые ошибки без запросов к внешним сайтам: повторы,
классификацию, переходы состояния, отсутствие дублей, восстановление, расписание,
историю, устаревшие результаты, безопасный вывод и ограничение доступа к настройкам.
